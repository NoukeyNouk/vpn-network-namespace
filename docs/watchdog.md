# Watchdog: наблюдение и расследование рестартов

По умолчанию WATCHDOG_MODE=observe. Этот режим никогда не вызывает setup-netns
или systemctl restart: лишь читает состояние и отправляет HTTP-пробы.
Не нужно включать auto, чтобы собирать диагностику обрывов.

## Обновление без перезапуска туннеля

Из обычного терминала хоста:

```sh
cd /home/noukey/Documents/Mega_vpn
sudo systemctl stop vpn-watchdog.service
sudo install -o root -g root -m 0755 vpn-watchdog.sh /usr/local/lib/mega-vpn/vpn-watchdog.sh
```

После этого, чтобы начать наблюдение:

```sh
sudo systemctl start vpn-watchdog.service
journalctl -u vpn-watchdog -f -o cat
```

Строка event=start должна содержать mode=observe. Если в /etc/mega-vpn/config
ранее явно задан WATCHDOG_MODE=auto, сначала поменяйте его на observe.
Остальные службы и маршруты эти команды не перезапускают.

## Что записывается

Каждая проба обоих адресов: scope (vpn/host), URL, код завершения curl,
HTTP-статус, полное время, время DNS, соединения и IP сервиса проверки.
kind различает DNS-ошибку, отказ соединения, таймаут, TLS-ошибку и неожиданный
HTTP-ответ. Это наблюдаемые симптомы, не диагноз блокировки провайдером.
Хост проверяется после отказа обоих VPN-адресов; успех хотя бы одного адреса
считается доступностью. Пробы двух адресов последовательные.

После порога неудач: event=incident и отчёт /var/log/mega-vpn/incident-*.log.
В отчёт входят локальные адреса/маршруты, PID/состояние служб, счётчики ошибок
из журнала sing-box за 3 минуты и повторные проверки перед решением.
Сырые логи приложений, пароли и конфиги в отчёты не копируются.
Отчёты содержат сетевые адреса; они доступны root, сохраняются последние 20.
Все решения также остаются в journald (срок хранения определяет система).

Полезные фильтры:

```sh
journalctl -u vpn-watchdog --since today -o cat | rg 'event=(incident|decision|restart|restart_result|recovered_without_action)'
sudo ls -lt /var/log/mega-vpn/
```

- recovered_before_action / recovered_without_action: связь вернулась без рестарта.
- observe_only: неисправность замечена, вмешательство запрещено режимом наблюдения.
- host_also_unreachable: проверочные адреса недоступны и с хоста, рестарт отменён.
- restart: причина, номер попытки в часовом окне, root_cause=undetermined.
- healthy_after_restart: все три последующие проверки успешны. Это временная
  связь событий, а не доказательство, что именно рестарт исправил проблему.
- no_sustained_recovery: хотя бы одна из трёх проверок после рестарта провалилась.
  Повторное вмешательство запрещено на 30 минут.
- command_failed: systemctl restart вернул ошибку; тот же запрет на 30 минут.
- restart_budget_exhausted: лимит рестартов исчерпан, продолжается наблюдение.

## Автоматический режим — только по явному выбору

В root-owned /etc/mega-vpn/config (без права записи группы и остальных):

```sh
WATCHDOG_MODE=auto
MAX_FAILURES=3
RECOVERY_COOLDOWN=120
MAX_RESTARTS=2
RESTART_WINDOW=3600
FAILED_RESTART_BACKOFF=1800
```

Чтобы применить настройки, перезапускают только vpn-watchdog.service.
Лимиты записываются в /run/mega-vpn ДО рестарта VPN; переживают рестарт
watchdog, но сбрасываются при перезагрузке компьютера. Успешное восстановление
не возвращает потраченную попытку в часовом окне. observe не расходует попытки.
Один shared flock исключает одновременные восстановления, включая --repair.

Наличие интерфейса больше не приводит к бесконечному повторному назначению
адреса/маршрута при каждом HTTP-сбое. setup-netns вызывается только при
отсутствии интерфейса/namespace и только в auto.

## Проверено офлайн

Тесты используют mock-команды, временные каталоги и реальные функции решения:
ошибки curl, HTTP redirect, остановленная служба, недоступность хоста, порог
ошибок, восстановление до вмешательства, observe без изменений, неудачный
и успешный рестарт, исчерпание/истечение бюджета, сохранение backoff, лимит
отчётов. Реальная сеть и systemd в тестах не вызываются.
