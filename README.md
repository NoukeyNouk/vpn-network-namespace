# Mega VPN

Обёртка над уже настроенным sing-box: приложения запускаются в отдельном
network namespace `hy2-vpn`, интерфейс `neko-tun` переносится туда из основного
namespace. Сам sing-box остаётся в основном namespace.

## Ограничения и требования

Нужны Linux, systemd, iproute2, bash, curl, util-linux, GNU coreutils.
Служба `sing-box.service` должна создавать TUN `neko-tun`. Её конфигурация
не входит в этот репозиторий. Перед включением нужно проверить, что настройки
маршрутизации sing-box не меняют маршруты хоста (в частности, автоматическую
маршрутизацию TUN), адрес интерфейса совместим с `172.19.0.2/28`, а исходящие
соединения sing-box идут через обычную сеть. Без этого изоляция хоста не гарантируется.
IPv6 здесь не настраивается; это IPv4-конфигурация, не универсальный VPN-клиент.
Не следует одновременно управлять этим namespace через другие VPN-службы.

## Установка и активация

`sudo ./install-services.sh` устанавливает root-owned копии в
`/usr/local/lib/mega-vpn`, unit-файлы и команды `run-vpn`, `vpn-ping`.
Он заменяет старые хуки проекта на пустые и перечитывает unit-файлы,
но не запускает, не останавливает и не включает службы.

Активация выполняется отдельно, когда допустим перерыв в соединении:

```sh
sudo systemctl enable sing-vpn.service vpn-watchdog.service
sudo systemctl restart sing-box.service sing-vpn.service vpn-watchdog.service
```

При миграции со старого `amnezia-vpn.service` сначала вручную остановите
и отключите его в согласованное окно обслуживания. Установщик этого не делает.
Изменения рабочего каталога не влияют на установленные копии до переустановки.

## Использование

```sh
run-vpn curl https://example.com
run-vpn firefox
vpn-ping
vpn-ping -c 4
vpn-ping --watch
vpn-ping --ip
```

Уже работающий браузер может передать новый URL старому процессу вне namespace.
Для браузера нужен отдельный экземпляр/профиль. Обёртка не изолирует IPC:
приложения, делегирующие запросы системным службам, требуют отдельной проверки.

`vpn-ping --fix` явно запрашивает восстановление, соблюдая общую блокировку
и cooldown. Остановленный sing-box эта команда не запускает.
`vpn-ping` измеряет время HTTP-запроса, включая DNS/TLS, а не ICMP RTT.
Проверка успешна лишь при успешном curl и HTTP 204 от одного из двух адресов.
Недоступность обоих проверочных сервисов не доказывает отказ всего VPN.

## Восстановление

Watchdog по умолчанию работает в режиме `observe`: только проверяет и пишет
журнал, не исправляет namespace и не перезапускает VPN. После трёх подряд
неудачных проверок при доступном интернете хоста сохраняет отчёт об инциденте.
Подробности и установка обновления: [docs/watchdog.md](docs/watchdog.md).

В режиме `auto` перед вмешательством повторно проверяет VPN и хост под
блокировкой. Не более двух рестартов в час, после неудачного рестарта —
пауза 30 минут. Настройки сохраняются через /etc/mega-vpn/config.
`vpn-ping --fix` явно запрашивает восстановление, даже при режиме observe,
но соблюдает лимиты и не запускает намеренно остановленный sing-box.

Остановка sing-vpn сохраняет namespace и resolver-файл, не переносит TUN
на хост. TUN принадлежит sing-box и исчезает при закрытии его дескриптора.
Это сохраняет окружение приложений, но не обещает сохранения TCP-соединений
после рестарта туннеля. Для удаления пустого namespace:
`sudo /usr/local/lib/mega-vpn/teardown-netns.sh --delete`.
При работающих процессах удаление отклоняется.

Опциональные настройки: `/etc/mega-vpn/config`, bash-присваивания, владелец root,
без права записи для группы/остальных. Пример:

```sh
NETNS=hy2-vpn
IFACE=neko-tun
VPN_ADDRESS=172.19.0.2/28
DNS1=1.1.1.1
DNS2=8.8.8.8
CHECK_INTERVAL=20
MAX_FAILURES=3
RECOVERY_COOLDOWN=120
```

После изменения namespace/интерфейса требуется запланированная миграция,
а не простое обновление файла у работающего VPN.

Журнал: `journalctl -u vpn-watchdog -u sing-vpn -u sing-box`.

## Проверка без запуска VPN

`bash tests/test-offline.sh` и `bash tests/test-watchdog.sh` используют подменённые команды для проверок HTTP
и `bash -n` для проверки синтаксиса. Сеть и systemd не вызываются.
Живые проверки переноса TUN, сна/пробуждения, DNS и маршрутов хоста нужно
проводить отдельно в тестовой VM или в согласованное окно обслуживания.
